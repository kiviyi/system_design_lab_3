# Отчет по проектированию БД

## Предметная область

Система хранит данные фитнес-трекера:

- пользователи
- упражнения
- тренировки пользователей
- упражнения, входящие в конкретную тренировку

## Сущности и таблицы

### `users`

Хранит учетные записи пользователей.

- `id` — первичный ключ
- `username` — уникальный логин
- `email` — уникальный email
- `first_name`, `last_name` — имя и фамилия
- `hashed_password` — хеш пароля

Ограничения:

- `PRIMARY KEY (id)`
- `UNIQUE (username)`
- `UNIQUE (email)`
- `CHECK` на базовую валидность email

### `exercises`

Каталог упражнений.

- `id` — первичный ключ
- `name` — название упражнения
- `description` — описание
- `muscle_group` — группа мышц

Ограничения:

- `PRIMARY KEY (id)`
- `NOT NULL` для обязательных полей

### `workouts`

Тренировки, принадлежащие конкретному пользователю.

- `id` — первичный ключ
- `user_id` — внешний ключ на `users`
- `name` — название тренировки
- `workout_date` — дата тренировки

Ограничения:

- `PRIMARY KEY (id)`
- `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`

### `workout_exercises`

Связующая таблица между тренировкой и упражнениями с параметрами выполнения.

- `id` — первичный ключ
- `workout_id` — внешний ключ на `workouts`
- `exercise_id` — внешний ключ на `exercises`
- `sets` — количество подходов
- `reps` — повторения
- `weight` — рабочий вес

Ограничения:

- `PRIMARY KEY (id)`
- `FOREIGN KEY (workout_id) REFERENCES workouts(id) ON DELETE CASCADE`
- `FOREIGN KEY (exercise_id) REFERENCES exercises(id)`
- `CHECK (sets BETWEEN 1 AND 100)`
- `CHECK (reps BETWEEN 1 AND 1000)`
- `CHECK (weight >= 0)`

## Связи между таблицами

- один пользователь `users` -> много тренировок `workouts`
- одна тренировка `workouts` -> много записей `workout_exercises`
- одно упражнение `exercises` -> может использоваться во многих тренировках

## Почему выбраны именно такие индексы

### `idx_workouts_user_id`

Нужен для быстрого поиска всех тренировок конкретного пользователя.

### `idx_workouts_user_date`

Нужен для двух частых сценариев:

- история тренировок пользователя
- статистика за период по диапазону дат

Композитный индекс позволяет фильтровать по `user_id` и сразу работать с сортировкой/диапазоном по `workout_date`.

### `idx_workout_exercises_workout_id`

Нужен для быстрого соединения тренировки с ее упражнениями.

### `idx_workout_exercises_exercise_id`

Нужен для выборок по конкретному упражнению и аналитики.

### `idx_exercises_muscle_group`

Полезен для фильтрации упражнений по группе мышц.

## Оптимизация запросов

В проекте выделены три типовых SQL-сценария:

1. История тренировок пользователя за период
2. Сводная статистика по тренировкам пользователя
3. Получение упражнений внутри конкретной тренировки

## Партиционирование

Для текущего объема данных партиционирование не требуется.

Если система вырастет, логичнее всего партиционировать таблицу `workouts` по дате тренировки:

- по месяцам
- либо по кварталам

Это даст выгоду для аналитики за периоды и упростит обслуживание старых данных.
